## 4. Задание 1. Эксперименты с формой и JSON

Страница `examples/forms-storage.html`, отдельный ключ `tip-js-practice-04:examples`.

### 4.1. Прогноз и факт

| № | Эксперимент | Прогноз | Фактический результат | Объяснение |
|---:|---|---|---|---|
| 1 | Отправка с пустым обязательным названием | Обработчик `submit` не сработает, `validity.valid === false` | Журнал после `requestSubmit()` **не изменился**; `validity.valueMissing = true`, `validationMessage = "Please fill out this field."`, `form.checkValidity() = false` | Браузер выполняет нативную проверку ограничений до генерации события `submit`. Прикладной обработчик не получает управления вообще |
| 2 | Название из одних пробелов | `required` будет выполнено, прикладное правило — нарушено | `validity.valid = true` при `value = "   "`, но `value.trim().length = 0`; после `setCustomValidity(...)` — `validity.valid = false`, `customError = true`, `reportValidity() = false` | `required` проверяет лишь непустоту строки. Смысловое правило «название не из пробелов» принадлежит модели, а `setCustomValidity` позволяет показать его стандартным механизмом браузера |
| 3 | Отправка корректных значений | Значения придут строками, `defaultPrevented` станет `true` | `typeof rawId = "string"`, `rawId = "20"`, `Number(rawId) = 20 (number)`, `Number("") = 0`, `rawTitle = "  Изучить localStorage  "`, `rawTitle.trim() = "Изучить localStorage"`, `defaultPrevented = true`, `formData.has("id") = true` | `FormData` отдаёт строки независимо от `type="number"`. Преобразование и нормализация выполняются явно. `Number("")` даёт `0`, поэтому пустую строку нужно отклонять отдельно |
| 4 | Чтение сохранённого значения | `getItem` вернёт строку, `JSON.parse` — объект | `typeof raw = "string"`, `raw !== null`; после разбора `typeof = "object"`, `Array.isArray(value.tasks) = true`, `value.tasks[0].id = 20 (number)` | В хранилище лежит строка. Объект появляется только после разбора; типы полей восстанавливаются из JSON |
| 5 | Повреждённый JSON | `JSON.parse` выбросит `SyntaxError` | Запись `{broken-json`: обработчик без `try/catch` прервался на строке разбора и не дописал следующую запись в журнал; вариант с `try/catch` перехватил `SyntaxError: Expected property name or '}' in JSON at position 1 (line 1 column 2)` | Исключение прерывает обработчик целиком. Поэтому граница чтения хранилища обязательно оборачивается в `try/catch`, а приложение переходит на исходный набор |

### 4.2. Фактический журнал страницы

```text
1. title.value = ""
   title.validity.valid = false
   title.validity.valueMissing = true
   title.validationMessage = "Please fill out this field."
   form.checkValidity() = false
2. title.value = "   "
   title.validity.valid = true (required выполнено)
   title.value.trim().length = 0
   прикладное правило нарушено: true
3. после setCustomValidity(...)
   title.validity.valid = false
   title.validity.customError = true
   form.reportValidity() = false
4. сработал обработчик submit
   event.defaultPrevented = true
   typeof rawId = string; rawId = "20"
   Number(rawId) = 20 (number)
   Number("") = 0
   typeof rawTitle = string; rawTitle = "  Изучить localStorage  "
   rawTitle.trim() = "Изучить localStorage"
   rawPriority = "high"
   idField.disabled = false; formData.has("id") = true
5. значение записано в localStorage
   строка = {"version":1,"tasks":[{"id":20,"title":"Изучить localStorage","completed":false,"priority":"high"}]}
6. typeof raw = string
   raw = "{\"version\":1,\"tasks\":[{\"id\":20,\"title\":\"Изучить localStorage\",\"completed\":false,\"priority\":\"high\"}]}"
   raw === null = false
7. typeof JSON.parse(raw) = object
   Array.isArray(value.tasks) = true
   value.tasks[0].id = 20 (number)
8. в ключ tip-js-practice-04:examples записана строка "{broken-json"
9. разбор без try/catch, raw = "{broken-json"
10. разбор в try/catch
   перехвачено SyntaxError: Expected property name or '}' in JSON at position 1 (line 1 column 2)
   приложение может подставить исходный набор вместо аварийной остановки
11. removeItem(tip-js-practice-04:examples) выполнен
   getItem вернул null
```

Между записями 1 и 2 нет шага отправки формы — это и есть результат эксперимента 1. Запись 9 не
имеет продолжения, потому что `JSON.parse` прервал обработчик: строка «разбор завершился без ошибки»
не появилась.

**Вывод по заданию 1.** HTML-ограничения проверяют форму ввода (непустота, числовой вид, длина) и
срабатывают раньше прикладного кода. Прикладное правило проверяет смысл значения в модели
(уникальность `id`, непробельное название, допустимый приоритет) и работает уже с результатом
`FormData`, то есть со строками. Ошибка разбора сохранённой строки — третий, независимый случай: она
относится не к вводу пользователя, а к состоянию внешнего хранилища, и обрабатывается только
`try/catch` с переходом на исходный набор.

## 6. Поток данных

Начальная загрузка:

```text
initialTasks + storageKey → loadTasks → currentTasks → setFormMode(null) → renderApp
                               │
                 source: initial | storage | fallback
```

Успешная операция:

```text
submit / click → validateTaskDraft → addTask | updateTask | setTaskCompleted | removeTask
                                                   │ ok
                                        новый currentTasks
                                                   │
                                   renderApp → saveTasks → сообщение
```

`renderApp` не читает и не записывает хранилище, поэтому повторная отрисовка не создаёт новых
записей JSON. Запись выполняется только после успешного изменения модели.

## 8. Проверки формы

| Случай | Уровень | Сообщение / поведение |
|---|---|---|
| Пустое название | HTML `required` | Нативное сообщение, `submit` не генерируется |
| Пустой идентификатор | HTML `required` + прикладной | `Укажите идентификатор задачи.` |
| Название из пробелов | Прикладной | `Укажите название задачи.` |
| Название длиннее 100 символов | HTML `maxlength` + прикладной | `Название не должно превышать 100 символов.` |
| `id` не целое или `≤ 0` | HTML `min`/`step` + прикладной | `Идентификатор должен быть положительным целым числом.` |
| Занятый `id` | Прикладной | `Задача с таким идентификатором уже существует.` |
| Недопустимый приоритет | Прикладной | `Выберите приоритет: low, medium, high.` |
| Редактируемая задача исчезла | Прикладной | `Редактируемая задача не найдена.` |

Фактический вывод ошибки при повторном идентификаторе (шаг 2 общего сценария):

```text
ошибка id: Задача с таким идентификатором уже существует.
ошибка title: ""
запись изменилась: false
```

Ошибки связаны с полями через атрибут `data-error-for` и `aria-describedby`, дополнительно
устанавливается `setCustomValidity(text)`. При событии `input` снимается ошибка **только того поля,
которое исправляют**: браузерная проверка № 12 отправляет форму с двумя ошибками, вводит корректное
название и убеждается, что сообщение у `title` исчезло (`customError = false`), а сообщение у `id`
осталось видимым.

## 10. Обязательная отладка

Точка останова поставлена в `handleFormSubmit` (`src/main.js`), на строке создания черновика из
`FormData`.

| Наблюдение | Успешное добавление | Повторный `id = 4` |
|---|---|---|
| Сырой черновик | `{ id: "20", title: "  Изучить localStorage  ", priority: "high" }` | `{ id: "4", title: "Повторный идентификатор", priority: "low" }` |
| `editingId` | `null` | `null` |
| Результат `validateTaskDraft` | `{ ok: true, value: { id: 20, title: "Изучить localStorage", priority: "high" } }` | `{ ok: false, errors: { id: "Задача с таким идентификатором уже существует." } }` |
| Результат сервисной операции | `addTask → { ok: true, tasks: [...5 задач] }` | не вызывалась: выполнение вышло из обработчика после `showFormErrors` |
| Записанная строка JSON | `{"version":1,"tasks":[...,{"id":20,"title":"Изучить localStorage","completed":false,"priority":"high"}]}` | не записывалась, значение ключа не изменилось |

В точке останова видно, что `id` приходит строкой `"20"` даже при `type="number"`, а крайние пробелы
названия снимает `validateTaskDraft`, а не браузер. В ошибочном сценарии обработчик завершается до
вызова `addTask`, поэтому «частично применённого» состояния не возникает. В режиме редактирования
`formData.get("id")` возвращает `null`, так как поле отключено, — подтверждено браузерной
проверкой № 9 (`formData.has("id") = false`).

## 14. Дополнительное задание, вариант А. Черновик формы

Реализован модуль `src/form-draft.js`: `loadDraft`, `saveDraft`, `removeDraft`, `isEmptyDraft`,
`DRAFT_VERSION = 1`. Черновик хранится по отдельному ключу `<ключ набора>:draft` в оболочке
`{ "version": 1, "draft": { "id": "...", "title": "...", "priority": "..." } }`.

Границы реализации:

- черновик содержит **сырые строки полей**, а не запись модели, и не может попасть в массив задач;
- он сохраняется только в режиме создания: при `editingId !== null` обработчик `input` ничего не пишет;
- пустой черновик (`id` и `title` после `trim` пусты) удаляет ключ, а не записывает «пустышку»;
- после успешного добавления, отмены редактирования, явной очистки и сброса данных черновик удаляется;
- повреждённый черновик удаляется и не подставляется в поля.

## 15. Ответы на контрольные вопросы

1. `submit` покрывает и клик по кнопке, и нажатие Enter в поле; обработка только `click` теряет клавиатурный путь.
2. `preventDefault` отменяет стандартное действие браузера (переход или отправку документа), но не прерывает выполнение обработчика — код после него продолжает работать.
3. Для обычных полей `FormData.get` возвращает строку, даже если у поля `type="number"`; для отсутствующего имени — `null`.
4. Отключённые элементы управления не считаются «успешными» и не включаются в `FormData`, поэтому в режиме редактирования `id` берётся из `editingId`.
5. HTML проверяет форму ввода: непустоту, числовой вид, диапазон и длину. Прикладная модель проверяет уникальность `id`, непробельность названия после `trim` и допустимость приоритета.
6. `required` считает непустой любую строку длины больше нуля, а пробел — обычный символ.
7. `setCustomValidity("")` снимает ранее установленную прикладную ошибку, иначе поле навсегда остаётся невалидным; `reportValidity()` запускает проверку и показывает сообщения браузера.
8. Чистая функция без DOM проверяется без браузера, повторно используется в других интерфейсах и не зависит от разметки.
9. По значению `editingId`: `null` — создание, число — редактирование существующей задачи.
10. `completed` — настоящий статус задачи, а не часть формы; изменение названия и приоритета не должно его обнулять.
11. `localStorage` хранит только строки; объект превращается в строку через `JSON.stringify` и обратно через `JSON.parse`.
12. Отсутствие ключа — нормальное состояние первого запуска (`source: "initial"`), повреждённая запись — ошибка (`source: "fallback"`), о которой сообщают пользователю.
13. Успешный разбор подтверждает только синтаксис JSON. Результатом может оказаться число, другая версия схемы или массив с повторяющимися `id`.
14. `version` позволяет отличить свою схему от чужой или устаревшей и отклонить её, а не истолковать неверно.
15. Частично применённые данные дали бы молчаливую потерю записей. Целиком отклонённый список приводит к понятному и воспроизводимому состоянию.
16. Явный аргумент показывает внешнюю зависимость и позволяет проверить модуль с объектом-имитацией — в проверках модулей используется `createMemoryStorage` и `createBrokenStorage`.
17. `saveTasks` возвращает `{ ok: false, error }`, изменение остаётся в памяти вкладки, а пользователь получает предупреждение.
18. `renderApp` вызывается многократно, в том числе при смене фильтра; запись в нём приводила бы к лишним и ошибочным сохранениям.
19. И фильтр, и режим редактирования — состояние интерфейса, а не модели. После перезагрузки форма открывается в режиме создания, а фильтр — «Все».
20. Иначе изменения общего набора появлялись бы в индивидуальном: наборы независимы и имеют разные исходные данные.
21. Чтобы автоматический прогон не удалял и не подменял рабочие данные пользователя.
22. `removeItem(storageKey)` затрагивает один ключ, а `clear()` — все ключи origin, включая данные других учебных страниц.
23. Область `localStorage` определяется origin — схемой, узлом и портом. Другой порт — другой origin и другое хранилище.
24. Ручными остаются клавиатурное управление, сообщения конкретного браузера, прогон индивидуального варианта, повреждение записи через DevTools, исключения хранилища и визуальная проверка интерфейса.

## 16. Вывод

В ПР4 интерфейс ПР3 дополнен формой, которая работает в двух режимах одной разметкой, и слоем
локального хранения. Главное, что стало явным, — три независимых уровня защиты данных. Нативные
ограничения HTML отсекают неправильный ввод и дают клавиатурное поведение, но ничего не знают о
модели. Чистая функция `validateTaskDraft` проверяет смысл значений и возвращает все ошибки сразу,
не касаясь DOM. Сервисные функции `addTask` и `updateTask` проверяют данные ещё раз, потому что
валидация интерфейса улучшает обратную связь, но не является гарантией: тот же принцип повторится на
сервере в ПР9–ПР10.

Отдельный результат — обращение с внешним хранилищем как с ненадёжным источником. Успешный
`JSON.parse` ничего не гарантирует, поэтому проверяются версия оболочки и полная схема каждой задачи,
а любое отклонение приводит к копии исходного набора и предупреждению, а не к аварийной остановке.
Исключения `getItem`, `setItem` и `removeItem` не выпускаются наружу: граница возвращает
`{ ok, error }`, и неудачная запись не откатывает уже выполненное изменение модели.

Разделение ключей `demo`, `variant` и `checks:*` показало, что область хранения — такой же ресурс,
как путь к файлу: она привязана к origin, и смена порта меняет видимые данные. Именно поэтому сброс
удаляет один рассчитанный ключ, а не вызывает `clear()`.

Все проверки проходят: 35 сценариев сервиса, 27 сценариев новых модулей и 23 браузерных сценария.
Общий контрольный сценарий и сценарий варианта 6 совпали с таблицами методички, включая итоговые
`50.0%` для общего набора и `66.7%` для варианта.
