## 4. Задание 2. Порядок асинхронного выполнения

**Прогноз до запуска** (метки A–F и собственная G):

```text
A, B, E, C, F, G, D
```

Обоснование прогноза: A, B и E — синхронный код текущего стека. `withAwait()` выполняется до
первого `await` сразу. Продолжения Promise (`C`, затем `F` после `await null`, затем `G`) —
микрозадачи. Таймер `D` — следующая макрозадача, поэтому он последним.

**Фактический вывод `npm run example:order`:**

```text
A — синхронный вывод в начале файла
B — синхронный вывод после регистрации операций
E — синхронная часть async-функции до await
C — первая микрозадача продолжения Promise
F — продолжение после await, тоже микрозадача
G — собственная микрозадача, добавленная в задании 2
D — обработчик таймера с нулевой задержкой
```

Прогноз совпал. Нулевая задержка `setTimeout` не означает вызов внутри текущего стека: сначала
опустошается очередь микрозадач.

## 5. Задание 3. Наблюдение за HTTP

Фрагмент фактического вывода `npm run example:fetch`:

| Запрос | status | ok | Content-Type | Форма тела |
|---|---:|:---:|---|---|
| `/health` | 200 | true | `application/json` | `{ data }` |
| `/tasks` | 200 | true | `application/json` | `{ data, meta }`, 12 задач |
| `/tasks?completed=false&priority=high` | 200 | true | `application/json` | 3 задачи, `meta.total = 3` |
| `/tasks/25` | 200 | true | `application/json` | `{ data: задача 25 }` |
| `/tasks/999` | 404 | **false** | `application/json` | `{ error.code: TASK_NOT_FOUND }` |
| `/tasks?unknown=1` | 400 | false | `application/json` | `{ error.code: INVALID_QUERY }` |
| `/categories` | 200 | true | `application/json` | 3 категории |
| `/debug/error` | 503 | false | `application/json` | `SERVICE_UNAVAILABLE` |
| `/debug/invalid-json` | 200 | true | `application/json` | `SyntaxError` при разборе |
| `/debug/text` | 200 | true | `text/plain` | обычный текст |

`fetch` при 404 и 503 **не отклоняется**: сервер доступен и вернул HTTP-ответ. `response.ok`
ложно, тело всё равно JSON. Повреждённый JSON при статусе 200 показывает, что успех протокола
не гарантирует пригодность данных.

## 7. Общий и предметный клиент

`buildUrl` использует `URL` и `URLSearchParams`: `false` и `0` сохраняются, `undefined`/`null`/`""`
пропускаются, входной объект не изменяется.

`requestJson` отдельно перехватывает отказ `fetch` (иначе HTTP-ошибка получила бы `kind: "network"`),
затем проверяет `Response`, статус, `204`, `Content-Type` и JSON. Сигнал тайм-аута и внешний сигнал
объединяются через `AbortSignal.any()` и передаются самому `fetch`.

`createTaskApi` проверяет фильтры **до** запроса. Логическое `false` не превращается в строку в
предметном коде: строковое представление создаёт `URLSearchParams`. После ответа проверяются поля,
уникальность `id` и равенство `meta.total` длине `data`.

## 8. Виды ошибок

| `kind` | Когда возникает | Пример прогона |
|---|---|---|
| `http` | статус вне `2xx` | `getTaskById(999)` → `status=404 code=TASK_NOT_FOUND` |
| `network` | ответа нет | остановленный сервер → `kind=network` |
| `invalid-response` | не JSON / неверная схема | `/debug/text`, `/debug/invalid-json` |
| `timeout` | истекло время | `/debug/delay` с `timeoutMs: 20` |
| `aborted` | внешний `AbortController` | `controller.abort()` до ответа |

## 9. Последовательное и параллельное ожидание

Два независимых `/debug/delay?ms=120`, по три прогона (`npm run example:delay`):

```text
прогон 1: последовательно 316 мс, параллельно 137 мс
прогон 2: последовательно 259 мс, параллельно 124 мс
прогон 3: последовательно 245 мс, параллельно 123 мс
среднее последовательно: 273 мс
среднее параллельно:     128 мс
```

`Promise.all` не создаёт параллельность сам: он ждёт уже запущенные Promise. При отказе одного
итоговый Promise отклоняется, остальные операции автоматически не отменяются. В `loadInitialData`
оба запроса начинаются до общего `await`. Искусственные задержки в итоговый код не входят.

## 14. Отладка

Точка останова в `requestJson` после получения `Response`. Для `/tasks/999`: `response.ok === false`,
`status === 404`, тело `{ error: { code: "TASK_NOT_FOUND", ... } }`, итоговый `kind` — `http`.
Для остановленного сервера `fetch` выбрасывает исключение до `Response`, `kind` — `network`.
Различие видно по месту перехвата: отдельный `try` вокруг `fetchFn`, обработка статуса — после него.

## 16. Вывод

Источник данных сменился: вместо `localStorage` — HTTP API. Главное — не путать доступность сервера
с пригодностью ответа. `fetch` при 404 возвращает `Response`; сеть молчит совсем иначе; JSON при
статусе 200 может быть повреждён или не соответствовать схеме. Общий клиент классифицирует это
полем `kind`, предметный модуль проверяет модель. Независимые запросы запускаются до общего
ожидания: среднее 128 мс против 273 мс последовательно на двух задержках по 120 мс.

Все проверки проходят: 18 + 26 + 13. Вариант 6 даёт id `[4, 16, 22, 25, 28, 34]` и `meta.total = 6`.
Клиент готов к подключению интерфейса в ПР6.
