## 3. HTTP-клиент и предметный API

`requestJson` расширен параметрами `method` и `body`. Допустимы `GET`, `POST`, `PATCH`, `DELETE`.
`GET` с телом отклоняется до сети. JSON-тело сопровождается `Content-Type: application/json`; запросы
без тела этот заголовок не получают. Успешный `204` возвращает `null` до `response.json()`.

`task-api.js` добавляет `createTask`, `updateTask`, `setTaskCompleted`, `deleteTask`, `resetDemoData`.
Сервер назначает `id` и начальный `completed: false`. После мутации контроллер не правит локальный
массив вручную, а повторяет `GET` с текущими фильтрами.

## 4. Асинхронные состояния

| Состояние | Когда | Интерфейс |
|---|---|---|
| `loading` | ответ ещё не получен | «Загрузка задач…», `aria-busy="true"` |
| `ready` | непустой список | карточки и «Найдено: N» |
| `empty` | успешный пустой результат | «Нет задач по выбранному фильтру.» |
| `error` | отказ запроса | сообщение и кнопка повтора |

`empty` — не ошибка. Кнопки мутаций блокируются на время запроса и разблокируются в `finally`.

## 5. Защита от устаревшего ответа

1. предыдущий `GET` отменяется через `AbortController`;
2. каждому запуску выдаётся номер, результат применяется только если номер совпал с последним.

Отмена — ожидаемое управление потоком, поэтому `kind: "aborted"` не показывается пользователю.

## 6. Индивидуальный вариант 6

Начальный фильтр `categoryId=2` («Проект»), ожидаемые id `[4, 16, 22, 25, 28, 34]`.

Сценарий: создать задачу категории «Проект» — карточка появляется в текущей выборке.

Фактически после `createTask({ title: "Изучить fetch", priority: "high", categoryId: 2 })` сервер
вернул `id = 35`, `completed = false`, и задача попала в `GET /tasks?categoryId=2`. Браузерная
проверка «Создание задачи добавляет карточку» это подтверждает.

## 10. Контрольные вопросы (кратко)

1. `fetch` считает 404/500 успешно полученным HTTP-ответом.
2. Сначала `ok`/статус, затем 204, затем `Content-Type`, затем JSON.
3. `POST` создаёт ресурс целиком, `PATCH` меняет указанные поля.
4. 201 и `Location` указывают на созданный ресурс.
5. У 204 нет тела — `json()` упадёт.
6. Preflight нужен для «непростых» запросов; `no-cors` скрывает JSON.
7. `empty` — успешный пустой набор; `error` — отказ.
8. Источник истины — API, не `localStorage`.
9. Повторный GET показывает подтверждённое сервером состояние.
10. Медленный старый ответ может перезаписать новый фильтр.
11. Отмена может не успеть: нужен номер запроса.
12. Отмена — не сбой пользователя.
13. Клиент улучшает UX; сервер обязан проверять сам.
14. `view` позволяет проверить контроллер без DOM.
15. Серверный текст недоверенный — только `textContent`.
